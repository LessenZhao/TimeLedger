# Work Evolution V0 正式规格

日期：2026-07-17

状态：Ready for Agent

主仓库：TimeLedger

主分支：`feature/work-evolution-v0`

## Problem Statement

用户每天通过 Codex 同时推进多个项目，也会进行不属于具体项目的思考。项目经常跨越多天和多个会话，同一个长期目标还可能经历不同 App、仓库、架构或实现路线。现有会话记录能够证明“讨论过什么”，Git 仓库和工作树能够证明“实际存在什么”，但这些原始记录没有被组织成可回看的工作价值地图。

因此，用户目前无法快速回答以下问题：

- 某一天具体做了什么；
- 每个项目当天取得了什么进展；
- 做出了哪些决策，为什么改变方向；
- 犯了哪些错误，哪些路线被证明走不通；
- 形成了哪些流程、原则、方法和可复用价值；
- 一个项目从最初目的到当前状态经历了怎样的演化；
- 一项结论来自哪些会话，是否与真实代码和工作树一致；
- 后来产生的新认识如何补回原来的项目，同时也出现在认识发生的当天。

如果这些内容没有被提炼、核实和归口，工作即使很多，也会表现为忙碌但不可见、不可回顾、不可积累。中断或失败的项目尤其容易被误判为“没有价值”，因为项目本身的结果、做项目过程中形成的方法、以及能够迁移到其他项目的经验没有被分别保存。

## Solution

在 TimeLedger 的 Mac App 中增加一个独立于 iPhone 连接的“工作沉淀”入口，建立一个轻量的 Work Evolution Ledger。系统以项目演化为长期主线，以 Project Day Slice 为基础记录单元，从同一份权威记录生成两个视角：

- 按天查看：还原当天所有有意义的 Codex 工作、项目动作、独立思考、决策、错误、方法和价值；
- 按项目查看：串联同一长期目标跨会话、跨日期、跨实现路线的关键演化节点和每日贡献。

原始事实来自 agent-session-archive 的干净会话归档以及相关 Git 仓库和当前工作树。用户在 Codex 客户端显式运行 `$evolution-ledger`，由 Codex 读取证据并生成候选 Proposal。Proposal 只能进入候选收件箱，不能直接修改权威记录。TimeLedger 负责验证引用、来源覆盖、幂等和用户保护规则，再把有效内容作为 candidate 导入。用户可以在 App 中确认记录，或添加自己的补充、纠正和后续反思。

V0 采用一个深模块 `EvolutionLedger` 作为唯一业务缝。归档读取、工作树核实、Proposal 导入、用户操作、按天投影、按项目投影和 Markdown 导出都必须通过这个模块。V0 使用单个本地结构化账本作为唯一语义真源；Markdown 只是派生导出，不承担双向编辑或权威存储。

## User Stories

1. 作为一名每天使用 Codex 工作的用户，我希望按日期看到当天做过的所有有意义工作，从而不再依赖模糊记忆判断一天是否有产出。
2. 作为一名同时推进多个项目的用户，我希望当天页面按项目列出动作与进展，从而快速理解时间和注意力去了哪里。
3. 作为一名会进行独立思考的用户，我希望不属于具体项目但值得保留的会话也出现在当天页面，从而不让重要思考因为无法归类而消失。
4. 作为一名重视完整性的用户，我希望当天所有来源会话都有明确去向，从而不会因为系统只挑选项目会话而漏掉其他工作。
5. 作为一名需要核对来源的用户，我希望当天显示的来源总数与来源列表严格一致，从而能判断提炼是否覆盖完整。
6. 作为一名需要审计结论的用户，我希望点开任一来源会话看到当天发生的消息片段，从而知道当天结论具体依据了什么。
7. 作为一名需要理解上下文的用户，我希望从当天片段切换到完整会话，从而理解跨天讨论的前因后果。
8. 作为一名需要精确追溯的用户，我希望消息保留来源、线程、事件、原文件、原行号和内容摘要，从而能定位到原始证据。
9. 作为一名使用跨天会话的用户，我希望一天只统计真实发生在当天的消息，从而不会把整个长会话错误算入每一天。
10. 作为一名位于亚洲时区的用户，我希望日界线固定按 Asia/Taipei 的自然日计算，从而避免 UTC 日期造成错日。
11. 作为一名在当天持续工作的用户，我希望处理任务先冻结证据截止时间，从而避免生成过程中新增消息导致来源账前后不一致。
12. 作为一名使用 `$evolution-ledger` 的用户，我希望处理任务自身在来源列表中可见但不产生价值，从而避免系统递归提炼自己的结果。
13. 作为一名项目所有者，我希望一个项目按长期目标识别，而不是按某个仓库、App 或架构识别，从而让方向变化仍属于同一演化过程。
14. 作为一名经历多次实现尝试的用户，我希望一个项目可以包含多条路线，从而区分长期目标和具体实现载体。
15. 作为一名回看旧项目的用户，我希望看到项目最初为什么开始，从而快速恢复当时的目标与约束。
16. 作为一名回看决策的用户，我希望看到关键决策、原因和被放弃的备选方案，从而理解当时为什么选择这条路。
17. 作为一名会改变方向的用户，我希望方向转变成为清晰的演化节点，从而知道项目何时、为何进入新路线。
18. 作为一名从失败中学习的用户，我希望失败路线和错误假设被保留，从而避免以后重新走同一条弯路。
19. 作为一名关心结果的用户，我希望看到项目当前形成了什么成果，从而区分讨论、实现、验证和实际使用。
20. 作为一名管理多个暂停项目的用户，我希望进展状态、结束方式和产物状态分开表达，从而避免用一个“完成/未完成”掩盖真实情况。
21. 作为一名需要回看演化的用户，我希望项目时间线只保留重要节点，从而既完整又不会退化成逐消息流水账。
22. 作为一名跨月回看项目的用户，我希望项目页面串联每天的 Project Day Slice，从而知道每一天对项目具体贡献了什么。
23. 作为一名关注项目本身价值的用户，我希望记录项目交付、流程或用途产生的价值，从而看到项目直接带来的积累。
24. 作为一名关注做事方法的用户，我希望记录做项目过程中形成的流程、方法和原则，从而把过程经验留给未来复用。
25. 作为一名同时做多个项目的用户，我希望识别能够迁移到其他项目的跨项目价值，从而提高后续项目的迭代速度。
26. 作为一名不希望被虚假量化的用户，我希望价值只记录类型和兑现状态而不打分，从而避免精确但没有意义的分数。
27. 作为一名面对中断项目的用户，我希望看到项目虽然中断但产生了哪些已兑现、待验证或未形成的价值，从而不把中断等同于浪费。
28. 作为一名后来才想明白问题的用户，我希望反思同时记录事情发生时间和认识形成时间，从而既能挂回原项目，也能出现在今天的价值地图中。
29. 作为一名拥有最终解释权的用户，我希望能对某一天、某个项目、某个切片或某个演化节点添加补充，从而补足自动提炼遗漏的信息。
30. 作为一名发现提炼错误的用户，我希望添加明确的纠正而不是让系统覆盖原始记录，从而保留可审计的修正过程。
31. 作为一名持续复盘的用户，我希望添加后续反思，从而让旧项目随着新认识继续演化。
32. 作为一名重视个人内容的用户，我希望用户添加的补充、纠正和反思永远不会被后续 Proposal 覆盖，从而放心使用自动重新生成。
33. 作为一名已经确认记录的用户，我希望 confirmed 的日期、项目和节点不会被静默重写，从而保持权威记录稳定。
34. 作为一名希望逐步校准系统的用户，我希望自动生成内容先以 candidate 进入，从而在确认前保持可检查、可修正。
35. 作为一名使用 Codex 处理证据的用户，我希望 Codex 只能写候选收件箱，从而不能绕过 TimeLedger 直接改变权威账本。
36. 作为一名需要安全导入的用户，我希望无效 Schema、无效消息引用或来源账不平衡时整包拒绝，从而避免半成功造成数据不一致。
37. 作为一名会重复运行任务的用户，我希望相同作业和相同内容重复导入时成为 no-op，从而可以安全重试。
38. 作为一名需要识别异常的用户，我希望相同作业标识但不同内容被报告为冲突，从而不会把不一致的候选静默合并。
39. 作为一名会在多个仓库工作的用户，我希望项目结论结合每个相关仓库的真实工作树核实，从而不只依赖会话自述。
40. 作为一名经常未提交代码的用户，我希望 staged、unstaged 和 untracked 文件也进入证据，从而看到 commit 之外的实际工作。
41. 作为一名需要判断可用性的用户，我希望构建或测试结果与代码状态分开记录，从而不会把“有代码”误认为“已经可用”。
42. 作为一名回填历史的用户，我希望系统明确说明当前工作树无法证明过去未提交状态，从而不把今天的状态伪造成历史事实。
43. 作为一名面对证据不足的用户，我希望系统标记 limitation、pending 或未核实，而不是自动补全结论，从而保持可信。
44. 作为一名非程序员用户，我希望 Mac App 启动后默认进入“工作沉淀”，从而无需先连接 iPhone 或理解技术入口。
45. 作为一名希望界面简单的用户，我希望“工作沉淀”内部只有“按天”和“按项目”两个主视角，从而快速找到所需信息。
46. 作为一名需要检查来源的用户，我希望会话内容在右侧 Inspector 中显示，从而不离开当前日期或项目上下文。
47. 作为一名希望长期保留数据的用户，我希望关闭并重新打开 App 后所有记录和用户补充仍然存在，从而把系统当作真实账本使用。
48. 作为一名希望保留可移植输出的用户，我希望按天和按项目生成可读 Markdown，从而可以备份、分享或在其他工具中阅读。
49. 作为一名重视单一真源的用户，我希望 Markdown 只是导出视图，从而不会因在 App 和文件中分别编辑而产生冲突。
50. 作为一名已有大量历史的用户，我希望先处理过去的 Codex 会话，从而让系统上线时立刻有可回看的价值，而不是等待未来积累。
51. 作为一名处理大量历史的用户，我希望历史回填按日期推进并保存检查点，从而中断后可以恢复而不必从头开始。
52. 作为一名不希望被小歧义阻塞的用户，我希望普通归类不确定时进入 pending，从而让其他日期和项目继续处理。
53. 作为一名关心项目身份准确性的用户，我希望只有高影响的项目合并或拆分歧义才需要我决定，从而把人工注意力用在关键位置。
54. 作为一名迭代产品的用户，我希望是否到位由实际可见结果决定，而不是强制运行三天或七天，从而按认知和验收反馈调整系统。
55. 作为一名使用多个设备但当前只验证 Mac 的用户，我希望 V0 不依赖手机同步，从而先验证工作沉淀逻辑本身。
56. 作为一名希望保持架构轻量的用户，我希望 V0 不引入数据库、云服务或后台模型调用，从而用最少必要结构验证核心闭环。

## Implementation Decisions

1. **唯一业务模块。** Work Evolution 的唯一高层业务缝为 `EvolutionLedger`。它负责准备证据、应用 Proposal、应用用户命令和读取投影。UI、CLI 和显式 Skill 不得绕过该模块直接修改语义真源。

2. **同源双视角。** 按天与按项目不是两套记录。Project Day Slice 是最小语义单元；按天投影聚合某日所有切片，按项目投影串联同一项目的跨日切片与演化节点。

3. **项目跟随长期目标。** Project 表达持续目标，Project Route 表达具体 App、仓库、架构或实现尝试。更换实现路线不会自动创建新项目。

4. **项目状态三分。** 进展状态固定为 exploring、active、paused、ended；结束方式固定为 completed、abandoned、replaced；产物状态固定为 not formed、pending validation、verified usable、in use、stopped。三者独立保存。

5. **价值不评分。** Value 只记录 project、process、cross-project 三种类型，以及 realized、pending、not formed 三种兑现状态。V0 不计算价值分数或排行榜。

6. **重要节点而非流水账。** Evolution Node 仅表示目的、关键决策、方向转变、失败路线、阶段结果、状态变化和后来反思。普通实现细节仍留在来源会话中。

7. **双时间语义。** 后来认识同时保存 happened at 和 recognized at。项目时间线按 happened at 还原演化；当天视图按 recognized at 显示新认识。

8. **会话与日切片分离。** 一个 Source Session 可以跨多天，只保存一次全局会话身份；每个自然日生成独立 Daily Source Slice，记录当天消息引用、分类和项目关联。

9. **精确日界线。** 所有日切片使用 Asia/Taipei，自然日采用闭开区间。来源数量只由实际落在时间窗且不晚于冻结截止时间的消息反推，不能使用线程更新时间、整段 Context Event 或 Collector 汇总数替代。

10. **全来源覆盖。** 每个有当天消息的会话必须属于 project、cross-project、independent thought、pending、excluded 或 processor 之一。来源总数、分类集合和来源列表必须完全对账，任何分类都不能静默隐藏。

11. **处理任务防递归。** 首条用户消息以 `$evolution-ledger` 开头的会话标记为 processor。processor 在来源审计中可见，但不能产生 Project Day Slice、Independent Thought、Value 或 Evolution Node。

12. **消息级证据。** Message Reference 保存来源、线程标识、事件标识、消息时间、角色、原文件、原行号和内容摘要。事件标识不是唯一永久键，验证时必须结合完整引用和内容摘要。

13. **完整会话不复制进账本。** 权威账本只保存会话身份和消息引用。Inspector 在需要时从 agent-session-archive 的 canonical clean archive 读取当天片段或完整会话。处理作业可以产生可删除的临时缓存，但缓存不是事实源。

14. **归档边界。** agent-session-archive 继续负责刷新干净会话归档，不承担价值提炼、项目识别或最终判断。EvolutionLedger 自己负责事件级时间切片、时区统一、覆盖计数和引用验证。

15. **工作树是第二证据源。** Worktree Evidence 至少包含仓库根、branch、HEAD、相关 commit、staged、unstaged、untracked、相关文件状态和实际执行过的验证结果。会话或 commit 单独存在都不能证明功能可用。

16. **历史证据诚实降级。** 当前工作树只能核实当前状态。无法恢复的历史未提交状态必须记录为 limitation，不能根据今天的文件反推过去已完成。

17. **单向 Proposal Inbox。** Codex 读取证据和现有账本后生成 Proposal，并通过完成文件原子投递到 inbox。Codex 不得直接写入权威账本，也不得生成 User Annotation 或 confirmed 状态。

18. **冻结输入。** 每个作业开始时保存 source cutoff、scope 和 source digest。作业完成后新增的会话或文件不属于该 Proposal，必须由下一次运行处理。

19. **整包校验。** Proposal 在写入权威记录前校验 Schema、作业身份、内容摘要、消息引用、项目引用、证据引用和来源覆盖。关键校验失败时整包拒绝，不做部分导入。

20. **幂等与冲突。** 相同 job identity 与相同 digest 的重复导入为 no-op；相同 job identity 但不同 digest 为 conflict；每次导入产生明确 Import Receipt。

21. **候选合并规则。** 新 candidate 可以加入；未确认 candidate 可以被后续 Proposal 更新生成字段；confirmed project、day 和 node 受到保护；任何用户内容都不参与自动覆盖。

22. **用户内容拥有最高优先级。** User Annotation 只由 App 中的用户命令创建，类型为 supplement、correction 或 reflection，可指向 day、project、Project Day Slice、Evolution Node 或 Source Session。

23. **单个本地语义真源。** V0 采用一个原子读写的本地结构化账本，保存项目、日期、演化节点、会话身份、用户补充和导入回执。数据规模或性能证据不足前不拆分数据库或多文件索引。

24. **损坏保护。** 账本解码失败时不得以空数据覆盖原文件；系统必须显示可诊断错误并保持原文件不变。成功写入采用临时文件加原子替换。

25. **查询投影。** EvolutionLedger 对外提供按天、按项目和全量快照。两个视角返回的同一 Project Day Slice 必须保持相同稳定身份。

26. **Mac App 是权威操作入口。** TimeLedger Mac App 增加一个“工作沉淀”侧边栏入口，并作为默认启动页。页面内部只暴露“按天”和“按项目”两个主视角。

27. **Source Inspector。** 来源会话从主视图选中后在右侧显示；支持当天片段与完整会话切换，并在不可读取时给出具体错误，而不是空白或静默失败。

28. **用户确认与补充。** App 支持确认 day、project 和 node，以及添加 supplement、correction、reflection。所有操作通过 EvolutionLedger 用户命令立即落盘并刷新投影。

29. **独立于手机。** 工作沉淀页面、Proposal 导入、用户确认和来源阅读均不依赖 iPhone 连接或 Mirror Session。V0 不改变手机数据模型或同步协议。

30. **App 不调用 AI。** App 只加载账本、扫描 inbox、验证和导入 Proposal、执行用户命令。语义提炼只能由用户在 Codex 客户端显式触发。

31. **显式 Codex 入口。** `$evolution-ledger` 只允许显式调用，首版支持 today、明确日期和 history 三种范围。它先刷新归档和冻结 cutoff，再准备证据、读取真实工作树、生成 Proposal 并原子投递。

32. **跨仓库部署边界。** TimeLedger 分支承载领域模型、深模块、CLI、Proposal 导入和 Mac UI。显式 Skill 的正式源属于现有 Skill 治理仓库，需要独立变更集和独立验证，但仍由本规格定义同一端到端契约。

33. **历史优先。** V0 首要业务数据是已有历史。history 从最早可处理日期按时间顺序运行，逐日保存 checkpoint；普通歧义进入 pending，高影响项目合并或拆分才请求用户判断。

34. **无固定运行天数。** V0 不以连续运行若干天作为完成标准。完成与否取决于真实日期、真实跨天项目和用户可见闭环是否通过验收。

35. **Markdown 是派生物。** 按天与按项目 Markdown 从权威账本生成，可重新生成，不能反向覆盖 App 数据。

36. **最小技术范围。** 复用现有 Swift、SwiftUI、Swift Package 和 Codable 基础；不引入新的外部运行时依赖、数据库、云账号或后台服务。

## Testing Decisions

1. **最高测试缝。** 主要验收通过 `EvolutionLedger` 的公开行为完成：给定归档与工作树 Fixture，prepare 产生可审计 Evidence Bundle；apply 导入 Proposal；read 分别返回一致的按天和按项目投影；用户命令能够确认记录并添加不可覆盖的注释。

2. **只测试外部行为。** 测试断言来源数量、投影内容、保护规则、文件结果和错误类型，不锁定内部数组顺序、私有辅助函数或具体 SwiftUI 视图层级。

3. **归档适配器契约测试。** 使用最小 JSONL Fixture 覆盖跨天长会话、UTC 与 UTC+8 混合时间、当天无消息但 updated at 变化、同线程重复文本、缺失原文件和 source line。断言以事件时间切片后的 distinct session 数为准。

4. **17 个来源对账测试。** 固定 Fixture 包含 17 个当天来源，并覆盖 project、cross-project、independent thought、pending、excluded、processor。断言总数、分类并集、列表行数和可打开来源均为 17。

5. **完整会话读取测试。** 给定一个跨天 Session，日查询只返回当天消息，完整会话查询返回全部干净消息；任一 Message Reference 被篡改时验证失败。

6. **工作树适配器契约测试。** 在临时 Git 仓库创建 commit、staged、unstaged 和 untracked 状态，断言快照如实报告。Git 命令失败、非仓库路径和不可读仓库不得返回 verified。

7. **历史限制测试。** 当 Proposal 声称历史未提交状态已验证但没有对应证据时拒绝或降级；当前工作树快照不得被标记成历史时点快照。

8. **Proposal 编码测试。** 所有新 DTO 进行 Codable round trip，并验证固定 Schema、稳定标识、source cutoff、source digest 和引用完整性。

9. **整包拒绝测试。** 无效 Schema、缺失消息、重复分类、来源计数不平、Proposal 试图写 User Annotation、Proposal 携带 confirmed 状态时，权威账本保持字节级不变。

10. **幂等与冲突测试。** 相同 job identity 与 digest 第二次导入返回 no-op；相同 job identity 与不同 digest 返回 conflict；两种情况都不产生重复 Project Day Slice。

11. **用户保护测试。** 先确认 day、project 或 node 并添加 supplement、correction、reflection，再导入覆盖相同目标的新 Proposal；确认内容和用户注释必须原样保留，并在回执中报告 protected。

12. **后来认识测试。** 一个 happened at 为旧日期、recognized at 为今天的节点，必须出现在项目旧位置和今天的认识列表中，但不能复制成两个不同节点。

13. **同源投影测试。** 同一 Project Day Slice 在按天与按项目查询中的稳定标识、内容和证据引用必须一致。

14. **持久化与重启测试。** 导入、确认和补充后重新构造模块，读取结果保持一致；损坏 JSON 不得触发空账本覆盖；原子写入中断后旧账本仍可读取。

15. **Inbox 集成测试。** App 扫描完成文件，成功导入后保存回执并归档输入；未完成临时文件不读取；拒绝的 Proposal 保留可诊断回执且不会反复静默尝试。

16. **Hub 状态测试。** Hub 的 Observable façade 在启动、手动刷新和 App 回到前台时加载最新快照；它不启动 Collector、不调用 Codex，也不依赖 Mirror Session。

17. **UI 构建与人工验收。** SwiftUI 不新增脆弱的内部层级测试。工程构建通过后，真实打开 App 验收一个日期、一个包含 17 个来源的日期、一个跨天项目、一次用户纠正和一次重启恢复。

18. **历史回填恢复测试。** history 在处理中断后从最近完成 checkpoint 继续；已处理日期不重复生成，pending 日期不阻塞后续日期。

19. **已有先例。** Codable、自然日、去重、用户锁、文件布局、导入幂等和 Hub store 测试沿用现有 EvolutionCore 与 EvolutionHubCore 的测试风格；手机 Mirror 测试不作为 Work Evolution 的主缝。

20. **完成证据。** 单元测试和构建成功只是工程证据，不能替代用户可见闭环。最终必须核对真实来源内容、真实工作树状态、页面来源数和项目演化可读性。

## Out of Scope

- iPhone 端工作沉淀页面；
- 手机到 Mac 的 Work Evolution 同步；
- SwiftData、SQLite 或其他数据库 Schema 变更与迁移；
- App 内模型调用、后台 AI、定时自动提炼；
- 云服务、登录、多用户、协作和权限系统；
- 向量数据库、Embedding、知识图谱或语义搜索；
- Markdown 双向编辑或把 Markdown 当权威真源；
- 价值数值评分、排名或自动 ROI；
- 自动消除所有 pending 或普通歧义；
- 修改 agent-session-archive 的保留/过滤规则；
- 恢复当前证据中不存在的历史未提交工作树；
- 用 commit、会话自述或当前代码单独宣称项目已经可用；
- 把现有扁平 Daily Review 或手机 Sync Batch 扩展成 Proposal 协议；
- 在 V0 引入多份语义真源、控制中心或复杂任务调度器；
- 自动 push、公开发布或变更远程仓库历史。

## Further Notes

- TimeLedger 的主实现只在 `feature/work-evolution-v0` 推进。
- 已存在的 Work Evolution 方案文件保持不变；本规格是新的正式输入，不覆盖旧文件。
- 当前工作树已有一组与本功能无关的 iOS 未提交改动和构建目录；实施时只能暂存本功能文件，不能使用全仓暂存。
- 显式 `$evolution-ledger` 的治理源位于另一个 Git 仓库。由于一个 Git 分支不能跨两个仓库，执行到 Skill 部署时需要单独分支和单独提交，但 Proposal 契约仍以本规格为唯一产品定义。
- Skill 安装或治理应用会修改本机运行入口，执行前必须单独获得用户确认；仅创建 TimeLedger 代码与本地运行数据不包含这项授权。
- 历史回填的完成标准不是日期数量，而是：任意旧日期能够还原当天价值，任意跨天项目能够还原关键演化，来源可以逐条打开，工作树结论有证据或明确 limitation，用户补充不会丢失。
- GitHub 发布版本应使用 `ready-for-agent` 标签；如果仓库尚无该标签，应先创建该标签，再发布与本文件内容一致的 Issue。
